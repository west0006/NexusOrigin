# 枢元 NexusOrigin 多智能体协作系统 完整设计方案

> 本方案基于《多智能体协作模块技术文档》（四级角色架构），结合中枢 Agent 动态能力分配、跨框架通信与流式可视化需求，形成一套 **完整、可落地、适合比赛演示** 的协作系统设计。涵盖业务逻辑、技术架构、核心 API、数据模型、交互界面与实现路径。

---

## 一、设计目标与核心定位

### 1.1 目标
- 构建 **框架无关** 的多智能体协作平台，支持 **CrewAI、LangGraph、AutoGen** 等异构框架的 Agent 统一接入与调度。
- 实现 **中枢 Agent** 根据各 Agent 实时注册的能力进行任务分解、匹配与分配。
- 提供 **流式可视化** 执行视图，展示任务分解、Agent 调度、进度、日志与成本。
- 集成 **全生命周期成本管理**（Token / 工具调用 / 资源），支持预算熔断。
- 纯本地、零付费演示能力（基于 Ollama + 开源模型）。

### 1.2 核心定位
- 不是单一框架的 Agent 平台，而是 **所有 Agent 的统一操作系统**。
- 核心差异化：
    - **动态能力注册与发现**
    - **跨框架统一调度与成本归因**
    - **任务执行全过程可视化**

## 二、系统架构与角色定义

### 2.1 四级角色架构（继承原文档）

| 角色 | 数量 | 职责 | 说明 |
|------|------|------|------|
| **中枢 Agent** | 全局唯一 | 任务接收、分解、分配、结果聚合、异常决策 | 领导 Agent，最高权限 |
| **审查 Agent** | 按需 | 监控任务执行，检测异常，问题分级上报 | 可多个，按领域划分 |
| **综合 Agent** | 全局唯一 | 阶段评审、结果整合、优化建议生成 | 结果中枢 |
| **组员 Agent** | 多个 | 执行具体子任务，上报进度与成本 | 不同框架实现的 worker |

**本次 MVP 重点实现**：中枢 Agent + 组员 Agent（支持多个框架注册），审查与综合 Agent 可简化为事件监听与日志聚合。

### 2.2 能力注册与发现机制（新增）

每个组员 Agent 在启动时向中枢 Agent 注册其 **能力列表**，格式如下：

```json
{
  "agentId": "researcher_crewai_1",
  "name": "研究员助手",
  "framework": "crewai",
  "endpoint": "http://localhost:8001/execute",
  "capabilities": [
    {
      "id": "research",
      "name": "信息检索",
      "inputSchema": { "topic": "string" },
      "outputSchema": { "summary": "string", "sources": "array" },
      "estimatedCostPerCall": 0.001,
      "estimatedDurationMs": 3000
    },
    {
      "id": "summary",
      "name": "文本摘要",
      ...
    }
  ],
  "status": "idle",
  "healthCheckUrl": "http://localhost:8001/health",
  "lastHeartbeat": 0
}
```

中枢 Agent 维护 **能力索引**（能力ID → Agent 列表），并定期通过心跳检测 Agent 存活状态。

### 2.3 任务分解与分配流程

1. 用户提交自然语言任务 → 中枢 Agent 调用 LLM 分解为子任务，每个子任务标注所需能力。
2. 中枢 Agent 查询能力索引，获取可执行该能力的 Agent 列表。
3. 根据 Agent 负载、历史成功率、预估成本等因素选择最优 Agent。
4. 将子任务（含输入数据、回调地址）发送给选中的 Agent。
5. Agent 执行并返回结果，中枢 Agent 聚合所有子任务结果，生成最终输出。

**示例**：
- 任务：“写一篇关于本地 LLM 的文章，并生成配图提示词”
- 分解：
    - 子任务1：收集本地 LLM 资料 → 能力 `research`
    - 子任务2：撰写文章 → 能力 `writing`
    - 子任务3：生成配图提示词 → 能力 `image_prompt`
- 中枢匹配：researcher_agent (CrewAI) → writer_agent (CrewAI) → designer_agent (LangGraph)

## 三、统一通信与事件协议

### 3.1 事件类型定义（流式可视化支撑）

| 事件类型 | 字段 | 说明 |
|---------|------|------|
| `task_decomposed` | `subtasks` | 任务分解结果 |
| `agent_selected` | `subtaskId`, `agent` | 为子任务选中的 Agent |
| `subtask_start` | `subtaskId`, `input`, `timestamp` | 子任务开始 |
| `subtask_progress` | `subtaskId`, `progress`, `message` | 中间进度（可选） |
| `subtask_tool_call` | `subtaskId`, `toolName`, `input`, `output` | Agent 内部工具调用 |
| `subtask_end` | `subtaskId`, `result`, `cost`, `durationMs` | 子任务结束 |
| `aggregation_start` | - | 开始聚合结果 |
| `final_result` | `result`, `totalCost`, `totalDuration` | 最终结果 |
| `error` | `subtaskId`, `errorMessage` | 错误发生 |

**传输方式**：Server-Sent Events (SSE) 或 WebSocket，由中枢 Agent 统一推送。

### 3.2 组员 Agent 标准接口

每个组员 Agent 需实现以下 REST 接口：

```
POST /execute
Request:
  {
    "taskId": "uuid",
    "capabilityId": "research",
    "input": { "topic": "..." },
    "callbackUrl": "http://localhost:8000/events"   # 可选，用于直接推送事件
  }
Response:
  {
    "taskId": "uuid",
    "result": { ... },
    "cost": 0.0012,
    "durationMs": 3400
  }
```

同时提供 `/health` 和 `/capabilities` 接口供中枢 Agent 查询。

## 五、全生命周期成本管理（简化 MVP）

### 5.1 成本计量维度

| 资源类型 | 计量方式 | 单价（模拟） |
|---------|----------|--------------|
| LLM Token（输入/输出） | 字符数 × 0.75 → Token | 输入 ¥0.001/1k，输出 ¥0.002/1k |
| Agent 工具调用 | 每次调用 | 固定 ¥0.001/次 |
| 子任务执行时长 | 毫秒 | ¥0.00001/秒 |

### 5.2 成本归因

每次子任务结束时，Agent 上报 `cost` 字段（JSON）。中枢 Agent 汇总并附加 `taskId`、`subtaskId`、`agentId`，存入本地 SQLite。

### 5.3 预算熔断

- 用户在成本面板设置月度预算（如 ¥5）。
- 中枢 Agent 每处理一个子任务前累加预估成本，若超过预算 95% 则拒绝新任务，并返回提示。
- 前端实时显示剩余预算。

### 5.4 前端成本仪表盘

复用现有 Dashboard，从 SQLite 读取数据，展示：
- 今日/本月总花费
- 按 Agent 成本占比饼图
- 按任务类型成本趋势
- 预算进度条（80% 黄色预警，100% 红色阻断）

## 六、技术实现要点

### 6.1 中枢 Agent 实现（Electron 主进程 + Node.js）

- 维护 `AgentRegistry`（SQLite 表 `agents`）。
- 实现 `TaskPlanner`：调用本地 Ollama 进行任务分解（Prompt 模板）。
- 实现 `Orchestrator`：调度、事件推送、成本聚合。
- 提供 SSE 端点供前端订阅。

### 6.2 组员 Agent 示例（Python）

```python
# generic_agent.py
from flask import Flask, request, jsonify
from langchain_ollama import ChatOllama

app = Flask(__name__)
llm = ChatOllama(model="qwen2.5-coder:3b")

@app.route('/execute', methods=['POST'])
def execute():
    data = request.json
    capability = data['capabilityId']
    inp = data['input']
    # 根据 capability 执行不同逻辑
    if capability == 'research':
        result = llm.invoke(f"收集关于 {inp['topic']} 的信息")
    elif capability == 'writing':
        result = llm.invoke(f"撰写文章：{inp['outline']}")
    # ... 模拟成本
    cost = len(result) / 1000 * 0.002
    return jsonify({"result": result, "cost": cost, "durationMs": 1200})

if __name__ == '__main__':
    app.run(port=8001)
```

### 6.3 前端组件结构

- `CollaborationLabPage.tsx`：主页面，包含流程图 + 日志区。
- `FocusPanel.tsx`：右侧滑出详情面板。
- `useCollaboration.ts`：管理 SSE 连接、事件处理、状态更新。

### 6.4 与现有 MVP 模块的集成

- 复用 `AgentChat` 组件作为基础对话。
- 复用 `CrossFrameworkAgent` 组件，但内部改为调用中枢 Agent 的 API。

## 七、核心数据模型

### 7.1 Agent 注册表

```sql
CREATE TABLE agents (
  id TEXT PRIMARY KEY,
  name TEXT,
  framework TEXT,
  endpoint TEXT,
  capabilities TEXT,  -- JSON array
  status TEXT,
  last_heartbeat INTEGER
);
```

### 7.2 任务执行记录

```sql
CREATE TABLE task_executions (
  id TEXT PRIMARY KEY,
  user_task TEXT,
  final_result TEXT,
  total_cost REAL,
  started_at INTEGER,
  finished_at INTEGER
);

CREATE TABLE subtask_executions (
  id TEXT PRIMARY KEY,
  task_id TEXT,
  agent_id TEXT,
  capability_id TEXT,
  input TEXT,
  output TEXT,
  cost REAL,
  started_at INTEGER,
  finished_at INTEGER,
  status TEXT
);
```

### 7.3 成本记录

```sql
CREATE TABLE cost_entries (
  id INTEGER PRIMARY KEY,
  task_id TEXT,
  subtask_id TEXT,
  agent_id TEXT,
  amount REAL,
  type TEXT,  -- 'token' / 'tool' / 'duration'
  details TEXT,
  timestamp INTEGER
);
```

## 八、演示与验收标准

### 8.1 演示流程（3 分钟）

1. 启动 Electron 客户端，进入“协作实验室”页面。
2. 输入任务：“写一篇关于本地 LLM 的科普短文，并配文生成提示词”。
3. 点击“启动”，观察：
    - 左侧流程图出现三个节点（research → writing → image_prompt）。

- [x] 所有 Agent 调用均基于本地 Ollama，无付费 API。
- [x] 流程图实时更新，节点状态与日志同步。

## 九、与原始文档的对应关系

| 原始文档模块 | 本方案实现 | 差异与增强 |
|-------------|------------|-------------|
| 四级角色架构 | 实现中枢 + 组员，审查/综合简化为事件监听 | MVP 阶段可简化，后期可扩展 |
| 统一状态管理 | 使用 SQLite + 内存缓存 | 分布式场景需 Redis，MVP 足够 |
| 分级通信与事件系统 | SSE + HTTP REST | 满足实时可视化需求 |
| 实时检测与问题上报 | 通过 Agent 心跳 + 子任务超时检测 | 未实现三级分级，可后续添加 |
| 阶段评审与结果整合 | 由中枢 Agent 聚合结果，未实现自动评审 | 评审可简化为用户确认 |
| 全生命周期成本管理 | 完全实现，支持多维计量与熔断 | 与原始设计一致 |
| 任务调度与资源管理 | 基于能力索引的匹配 + 负载均衡 | 动态负载均衡预留接口 |

## 十、后续扩展方向

1. **引入审查 Agent**：自动对中间结果质量评分，不通过时触发修正。
2. **支持更多框架**：AutoGen、MetaGPT 通过相同能力注册接口接入。
3. **分布式部署**：中枢 Agent 集群 + Redis 状态共享。
4. **强化成本模型**：接入真实模型网关（Ofox/302.AI）获取精确价格。
5. **智能任务分解优化**：基于历史执行数据微调分解 Prompt。
